1. Résumé exécutif

La collecte a porté sur le catalogue produit de LambdaTest E-commerce Playground (S17), qui tourne sous OpenCart. Le site sert son contenu en HTML côté serveur — constaté via curl, sans exécution de JavaScript. Au final, 60 produits ont été collectés (nom, prix, devise, catégorie, url, image, disponibilité), exportés en JSONL, sans aucun rejet ni doublon.
La principale difficulté a été que la disponibilité n'existe que sur la fiche produit, pas sur le listing, ce qui impose une requête supplémentaire par produit. Ce point a été géré via un plafond configurable (60) et un délai d'1s entre les requêtes, pour rester raisonnable vis-à-vis du serveur.

2. Diagnostic de la cible

2.1 Périmètre et règles d'accès

On a choisi de scraper une seule catégorie du site (celle avec path=17), en suivant le parcours normal d'un visiteur : menu → catégorie → pages suivantes → fiche produit. Résultat : 60 produits récupérés sur 4 pages de 15.
Avant de scraper, on a vérifié qu'on avait le droit en lisant le fichier robots.txt du site (ce fichier dit quelles pages un robot a le droit ou non de visiter). Au lieu de juste le lire à l'œil, on l'a vérifié avec du code (can_fetch()), qui répond True pour les 3 types de pages qu'on visite : la page catégorie, les pages suivantes (pagination), et les fiches produit.
Le site interdit bien certaines choses, mais seulement des URLs bizarres comme ?page= sans numéro derrière — pas les vraies pages de pagination qu'on utilise (?page=2, ?page=3...). Donc ça ne nous concerne pas.
Le site ne demande pas de délai particulier entre les requêtes (le Crawl-delay n'est pas défini). Mais par prudence, le scraper attend quand même 1 seconde entre chaque requête, et n'envoie jamais deux requêtes en même temps.

3. Objet et modèle de données

Nom de l'objet principal : Product (produit du catalogue)

Champ Type Obligatoire ? Source Normalisation / règle d'absence
id str non (utilisé pour dédup/id, pas rejeté si absent) product_id extrait de l'URL (query string) None si absent de l'URL
name str oui listing : h4.title a espaces normalisés (normalize_text) ; absent → objet rejeté
price float oui listing/detail : span.price-new '$146.00' → 146.0 (normalize_price) ; absent → objet rejeté
currency str non symbole du prix ($, £, €) → code ISO None si prix illisible
category str non fiche détail : dernier maillon non actif du fil d'Ariane None si non trouvé ; dépend du chemin de navigation (limite documentée)
url str oui listing : href du lien produit, résolu en absolu absent → objet rejeté
image_url str non listing : data-src (lazy-load) ou src None si aucune image
availability str non fiche détail : <li> 'Availability:' + badge normalisé en in_stock/out_of_stock/preorder ; None si introuvable (log warning)

Règle d'identifiant : Extraction du paramètre query `product_id` depuis l'URL canonique d'OpenCart.

Règle de déduplication : Déduplication basée sur `id` (ou `url` en secours), en conservant uniquement la première occurrence.

Distinction absent / vide / nul : Si un champ n'est pas trouvé dans la page, il est affecté à la valeur Python `None`. Aucune chaîne vide `""` n'est générée. Si un champ obligatoire (`name`, `price`, `url`) vaut `None`, l'objet complet est rejeté par `build_record()`.

5. Ancrage des sélecteurs

Champ Ancrage retenu Pourquoi plus stable que… Si l'ancrage disparaît demain

availability on cherche le <li> contenant le libellé 'Availability:' (avec .ls-label) puis on lit le <span class="badge"> associé plus robuste qu'un sélecteur basé sur la position dans la liste (ex. "le 4e <li>"), car l'ordre des infos (fabricant, vues, points, disponibilité) n'est pas garanti d'une fiche produit à l'autre. On s'ancre sur le libellé métier visible par l'utilisateur plutôt que sur sa position availability vaut None et un warning explicite ("Disponibilité introuvable...") est loggé , l'erreur est visible dans les logs plutôt que de produire silencieusement un enregistrement incomplet.

6. Choix des outils

Besoin Outil retenu Pourquoi Alternative envisagée Pourquoi écartée
Acquisition requests Simple, suffisant : le HTML contient déjà les données (pas de rendu JS nécessaire) Playwright/Selenium Coût (dépendance navigateur, lenteur, fragilité) injustifié car aucune donnée cible n'est chargée en JS
Extraction BeautifulSoup + lxml Parsing HTML robuste et lisible avec sélecteurs CSS Expressions régulières sur le HTML brut Beaucoup plus fragile face aux variations de balisage, illisible à maintenir
Modèle et validation dataclass + fonctions pures (normalize.py) Règles de normalisation/validation explicites, testables isolément Librairie de validation type pydantic Complexité et dépendance non justifiées pour 8 champs et quelques règles simples
Vérification Script de contrôle exécutable (tests/verif.py) sur fixtures HTML Rejoue l'extraction sans réseau, rapide à écrire et à expliquer pytest (3 tests automatisés) Les deux valent les mêmes points (énoncé) ; le script unique suffisait au besoin sans dépendance de test supplémentaire
Export json (stdlib), écriture JSONL Format simple, une ligne par objet, lisible et standard CSV CSV gère mal les champs optionnels/None et les valeurs imbriquées ; JSONL colle mieux au schéma

Décision 1 : requests+BeautifulSoup vs navigateur piloté : justifié tant que le site sert du HTML déjà complet ; le compromis assumé est que si le site passait un jour au rendu côté client (JS), il faudrait migrer vers Playwright.

Décision 2 : Visite systématique de chaque fiche produit : nécessaire car le champ availability n'existe que sur la page détail, pas sur le listing. Compromis assumé : cela double le nombre de requêtes HTTP, d'où l'importance des garde-fous MAX_ITEMS (plafond) et du délai configurable entre requêtes (pour rester poli envers le serveur cible).

9. Limites et amélioration prioritaire

  1. Le champ category dépend du chemin de navigation : un même product_id peut afficher une catégorie différente selon le path= utilisé pour y accéder (constaté : "Software" via path=17, "Tablets" via path=57 pour le même produit) — ce n'est pas une taxonomie fixe.
  2. Aucun mécanisme de reprise (checkpoint) : une interruption réseau en cours de collecte oblige à relancer depuis le début, sans reprendre où on s'était arrêté.
  3. La stabilité dépend entièrement des classes CSS du thème OpenCart actuel (product-thumb, price-new, ls-label...) : une refonte visuelle du site casserait l'extraction sans prévenir autrement que par des champs vides et des warnings.

Amélioration prioritaire : ajouter un mécanisme de reprise (sauvegarder les product_id déjà traités), car c'est la limite qui coûterait le plus cher en cas de collecte plus large que 60 produits : sans ça, la moindre coupure réseau oblige à tout refaire.
